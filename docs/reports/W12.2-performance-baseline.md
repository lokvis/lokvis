### 2.4 首屏 LCP 预估

基于静态产物推断（无浏览器实测）：

- **首屏必需资源**：`index.html` (11 KB) + `client.js` (180 KB) + `react.js` (12 KB) + `Playground.js` (444 KB，含 CodeMirror) ≈ **647 KB**（未 gzip）
- **gzip 后预估**：~180-220 KB（JS gzip 比 ~3x）
- **LCP 预估**：3G 慢速 (~1.5 Mbps) ~3-4s；4G ~1-2s；宽带 <1s

> **优化机会（W21 性能优化任务）**：`Playground.js` 444 KB 含 CodeMirror，首屏 Code Editor 不一定打开，可改为按需 `import()` 懒加载，预计可削减 ~400 KB 首屏负载。W12.4 文档定稿后此 chunk 拆分将更清晰。

## 3. WASM 加载基线

**关键事实**：当前 Phase 1 MVP **完全零 WASM**。

| 引擎 | WASM 依赖 | 加载策略 | 状态 |
|------|----------|----------|------|
| `engine-image` | 无（Canvas + createImageBitmap） | 不适用 | ✅ MVP |
| `engine-pdf` | pdf-lib（计划） | stub | Phase 2 |
| `engine-video` | ffmpeg.wasm（计划） | stub | Phase 2 |
| `engine-audio` | Web Audio API / WASM（计划） | stub | Phase 2 |
| `engine-ai` | transformers.js（计划） | stub | Phase 2 |

**结论**：W12.2 WASM 加载指标在 Phase 1 Alpha 阶段**不适用**（N/A）。零 WASM 是 MVP 的性能优势——首屏不阻塞、无需 COOP/COEP 即可运行（虽然 cloud `apps/web/public/_headers` 已配 COOP/COEP 供 Phase 2 使用）。

**Phase 2 接入 ffmpeg.wasm 后**的加载策略已设计（PROJECT_PLAN W15.2/W21.2）：
- 懒加载：用户触发视频工具才加载（`engine-video/src/lazy.ts`，W15.2 待实现）
- SW 预缓存：playground 安装后后台预加载 top 5 engine（W15.7 待实现）
- HTTP/2 分片 + 不可变缓存（W21.2 待实现）

## 4. 50 图批量耗时基线

### 4.1 测试用例

文件：`packages/runtime/src/__tests__/integration/batch-resize.test.ts`（13 测试）

测试场景：
- 50 个图片 Asset 通过 `BatchProcessor.enqueue()` 入队
- 并发槽位 free=4 / pro=16
- 每项：`importAsset` → `run(resizeWorkflow)` → 输出 AssetId
- 使用 fake image.resize 实现（Node 环境，不调真实 Canvas，仅测调度与内存治理）
- MemoryGuard 压力注入模拟（不依赖真实大图）

### 4.3 真实浏览器预估

fake execute 不调 Canvas，真实浏览器需叠加：

| 阶段 | 单项预估（1920×1080 JPEG） | 50 项并发 4 总耗时预估 |
|------|---------------------------|----------------------|
| `importAsset`（File → Blob → AssetStore） | 5-15ms | 已含 |
| `createImageBitmap` decode | 30-80ms | 串行 ~2-4s（并发 4） |
| Canvas resize drawImage | 10-30ms | 串行 ~0.5-1.5s |
| `canvas.toBlob` encode | 20-60ms | 串行 ~1-3s |
| AssetStore.create（OPFS / IDB） | 5-20ms | 已含 |
| **合计单项** | **70-205ms** | — |
| **50 项 / 并发 4** | — | **~5-15s**（取决于硬件） |

> **基线结论**：50 图批量 resize 在中端笔记本（M1 / i5-12）预估 5-10s，移动端可能 15-30s。Alpha 验收通过；M1.2 Beta 阶段若实测超 15s 需触发 W21.4 Worker Transferable 优化。

## 7. 浏览器端动态指标采集方案（待 playground 部署）

playground.lokvis.dev 部署后，在 W12.7 缓冲期或 W16.5 Lighthouse 跑分任务中执行：

### 7.1 Lighthouse 跑分

```bash
# 安装
pnpm add -Dw lighthouse

# 跑分（playground 部署后）
npx lighthouse https://playground.lokvis.dev/ \
  --output=html --output-path=./docs/reports/lighthouse-playground.html \
  --preset=desktop \
  --throttling-method=devtools
```

目标（PROJECT_PLAN §6 W16.5）：
- LCP < 2.5s
- FID < 100ms
- CLS < 0.1

### 7.2 真实用户监控（RUM）

通过 12.3 Sentry 接入后，配置 Web Vitals 自动采集：
- `Sentry.captureMessage('web-vitals', { extra: { lcp, fid, cls, ttfb } })`
- 阈值告警：LCP > 4s 触发 Performance Issue

### 7.3 50 图批量真实耗时

在 playground `/tools/batch` 页面埋点：
```ts
const t0 = performance.now();
await batchProcessor.enqueue(items);
const elapsed = performance.now() - t0;
runtime.eventBus.emit({ type: 'batch:completed', elapsed_ms: elapsed, count: items.length });
```
通过 Sentry 上报 `batch:completed.elapsed_ms`，P95 < 15s 为 Alpha 通过线。
