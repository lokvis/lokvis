## 一、项目定位

**Lokvis** 是一个 **本地优先的浏览器工作空间平台（Local-first Browser Workspace Platform）**，通过 WebAssembly（WASM）、PWA、OPFS 等现代浏览器能力，将图像、视频、PDF、音频、AI 推理等生产力工具完整迁移至浏览器内本地执行，并以 **Runtime + Workflow + Plugin + Marketplace** 的开放架构构建可持续演进的工具生态。

一句话定位：

> **Everything runs in your browser. No uploads. No servers. No compromises.**

## 二、核心命题

### 2.1 传统在线工具站的结构性矛盾

| 矛盾维度 | 传统模式（iLovePDF/Smallpdf 等） | Lokvis 模式 |
|----------|--------------------------------|-----------|
| **数据隐私** | 用户文件必须上传云端 | 文件永不离设备，零上传 |
| **计算成本** | 服务器 CPU/存储随流量线性增长 | 计算发生在用户浏览器，服务器成本近零 |
| **单点 vs 平台** | 工具孤岛，无工作流编排 | 统一 Runtime，可编排跨工具工作流 |
| **分发方式** | 一次性 Web 访问，无留存 | PWA 安装，桌面/移动端持久留存 |
| **生态壁垒** | 工具同质化，无开发者参与 | Workflow 市场 + Plugin SDK 形成网络效应 |

### 2.2 核心洞察

1. **技术拐点已至**：OPFS（90%+ 覆盖）、WebCodecs（85%+）、WASM（成熟）、SharedArrayBuffer（85%+）四项关键浏览器 API 在 2024-2025 年同时进入主流可用阶段，"浏览器即操作系统"从口号变为现实。

2. **市场空白明确**：
   - 传统工具站（iLovePDF 月访问 2.83 亿次）依赖云端处理，隐私与成本是软肋
   - WASM 工具（Squoosh、ffmpeg.wasm、Photopea）已验证技术可行性，但都是单点工具
   - 工作流平台（n8n、Zapier）连接 API，不处理本地文件
   - **"本地处理 + 工作流编排 + 工具市场"是明确的无人区**

3. **成本结构颠覆**：基于 Cloudflare 全栈（Workers + R2 + D1 + Pages），MVP 月运营成本可压缩至 **$5-20**，对比传统云端处理工具可节省 70-90% 基础设施成本。

4. **创作者经济红利**：全球创作者经济 2024 年规模约 2500 亿美元，2.07 亿创作者中大量群体需要批量处理媒体素材，付费意愿明确。

## 三、产品架构

### 3.1 五层架构总览

```
┌─────────────────────────────────────────┐
│           UI Layer (Astro + React)      │  ← SEO 内容 + Workspace SPA
├─────────────────────────────────────────┤
│         Workflow Layer (JSON 声明式)     │  ← 可分享、可售卖的工作流
├─────────────────────────────────────────┤
│           Runtime Layer (浏览器内核)     │  ← 调度、状态、事件、历史
├─────────────────────────────────────────┤
│         Capability Layer (能力注册)      │  ← Resize/Compress/OCR 等抽象
├─────────────────────────────────────────┤
│      Engine Layer (WASM / WebCodecs)    │  ← FFmpeg/ImageMagick/pdf-lib
└─────────────────────────────────────────┘
```

### 3.2 双仓库 Open Core 架构

```
GitHub Organization: lokvis
├── lokvis-open     (开源 Monorepo)
│   ├── apps/      (web, docs, playground)
│   └── packages/  (runtime, schema, sdk, plugin-sdk, ui, engines)
└── lokvis-cloud    (闭源商业 Monorepo)
    ├── apps/      (api, dashboard, marketplace)
    └── packages/  (auth, billing, sync, analytics)
```

**核心依赖原则**：`lokvis-cloud` 依赖 `lokvis-open`，反向永不成立。

### 5.2 核心商业逻辑

- **免费层**：基础工具 + 浏览器运行 + 离线可用 + 无需登录

## 六、技术栈选型

| 层级 | 技术 | 选型理由 |
|------|------|---------|
| 内容层 | Astro 7 | SEO 优先，80% 内容驱动 |
| Workspace UI | React 19 | 复杂交互生态成熟 |
| 状态管理 | Zustand | 轻量、无模板代码 |

| 本地数据库 | Dexie (IndexedDB) | 元数据存储 |
| 文件系统 | OPFS + File System Access API | 大文件持久化 |
| 边缘计算 | Cloudflare Workers | 全球低延迟 API |
| 对象存储 | Cloudflare R2 | 零出口费 |
| SQL 数据库 | Cloudflare D1 | 元数据存储 |
| 缓存 | Cloudflare KV | Session/Feature Flag |

## 七、关键风险与应对

| 风险等级 | 风险点 | 应对策略 |

## 九、结论

Lokvis 项目的核心价值主张可总结为三点：

1. **技术拐点红利**：浏览器能力（WASM/OPFS/WebCodecs）在 2024-2026 年同时成熟，"浏览器即 OS"从愿景变为可落地产品。

2. **成本结构颠覆**：本地优先架构使服务器计算成本趋近于零，Cloudflare 全栈使 MVP 月成本控制在 $5-20，毛利率显著优于传统云端工具站。

3. **生态壁垒潜力**：通过 Runtime + Workflow Schema + Plugin SDK + Marketplace 的开放架构，有机会建立"浏览器工作流运行时"的事实标准，形成长期网络效应。

**最大风险不是技术，而是分发与生态冷启动**。建议采取"垂直切入 → 工作流积累 → 平台开放"的三阶段策略，第一年只服务一个高频职业人群（建议：内容创作者或电商卖家），避免过早横向扩张。
