`@lokvis/runtime` 是 Lokvis 内部的“浏览器操作系统”。它唯一的职责是 `Input → Run → Output`：持有资产、分发能力、追踪历史、在 Worker 中隔离重计算，并对外暴露一个既不感知 React、也不感知 Redux 或 Cloudflare 的接口。本文档梳理了该包的每个模块、契约与扩展点。

> **版本：** `RUNTIME_VERSION = '0.1.0'` · **Schema 版本：** `v1` · 关于本包所执行的五层依赖规则，参见 [架构总览](../architecture)。

## `LokvisRuntime` 契约

`types.ts` 定义了公共接口。它被拆分为五个领域，便于使用者按需检索，而无需通读整个接口。

```typescript
interface LokvisRuntime {
  // ─── 工作流执行 ─────────────────────────────────
  run(workflow, inputs, options?): Promise<WorkflowResult>;
  cancel(workflowId): Promise<void>;
  pause(workflowId): Promise<void>;
  resume(workflowId): Promise<void>;
  getCurrentOutputs(workflowId): Promise<AssetId[]>;
  disposeWorkflow(workflowId): Promise<void>;

  // ─── 历史与 undo/redo ────────────────────────────────
  history(workflowId): Promise<HistoryEntry[]>;
  getHistoryState(workflowId): Promise<{ entries: HistoryEntry[]; cursor: number }>;
  undo(workflowId): Promise<void>;
  redo(workflowId): Promise<void>;
  jumpTo(workflowId, index): Promise<void>;

  // ─── 资产管理 ───────────────────────────────────
  importAsset(source): Promise<AssetId>;
  getAsset(id): Promise<Asset>;
  exportAsset(id, format?): Promise<Blob>;
  readAssetExif(id): Promise<ExifData | null>;
  removeAsset(id): Promise<void>;
  listAssets(): Promise<Asset[]>;
  getStorageUsage(): Promise<{ usage: number; quota: number }>;

  // ─── 能力查询 ─────────────────────────────────
  capabilities(): Promise<Capability[]>;
  hasCapability(name): Promise<boolean>;

  // ─── MCP 暴露 ───────────────────────────────
  toMcpManifest(options?): McpManifest;

  // ─── 顶层状态 ────────────────────────────────────
  readonly version: string;
  readonly status: 'idle' | 'running' | 'paused' | 'error';
  readonly eventBus: EventBus;
  readonly isPro: boolean;
  readonly batch: BatchProcessor;
}
```

`run()` 接受 `AssetId[] | Asset[]`。`RunOptions.appendHistory` 会保留既有历史栈，使连续的 `run()` 调用链接成同一条 undo/redo 时间线（playground 的 `HistoryDemo` 借此实现堆叠滤镜）。默认为 `false` —— 每次 `run()` 重置栈，对应“重新执行”的语义。

## `createRuntime()` 构造流程

`createRuntime(config?)` 是 `async` 的，因为环境探测（OPFS / IDB）无法同步完成。工厂按顺序装配六个子系统，然后在返回实例前预加载并恢复任何已持久化的历史快照。

<Mermaid source={`flowchart TD
  A["createRuntime(config)"] --> B["createAssetStore()\nOPFS → IDB → Memory"]
  B --> C["createHistoryStore()\nIDB or undefined"]
  C --> D["new LokvisRuntimeImpl({...config, assetStore, historyStore})"]
  D --> E["wrapAssetStoreWithQuota()\nimport/create/remove serialized"]
  E --> F["new CapabilityRegistry(engineStrategy)"]
  F --> G["new WorkflowExecutor({assetStore, registry, eventBus})"]
  G --> H["new MemoryGuard({budget, assetStore})"]
  H --> I["new BatchProcessor({runtime, eventBus, isPro, memoryGuard})"]
  I --> J["eventBus.on('node:finished', recordHistoryFromNodeEvent)"]
  J --> K["impl.loadPersistedHistory()\nrestore undo/redo from IDB"]
  K --> L["return impl as LokvisRuntime"]
`} />

直接构造 `LokvisRuntimeImpl`（不通过工厂）会回退到 `MemoryAssetStore` 并打印告警 —— 异步的 OPFS/IDB 探测只能发生在异步工厂内部。生产代码应始终经由 `createRuntime()`（或在 SDK 中使用 `createLokvis()`）。

## 五大子系统

### 1. AssetStore —— 三级回退 + 配额包装

`createAssetStore({ preferOpfs: true })` 按顺序探测后端，任一失败即降级。最终回退（`createMemoryAssetStore`）始终可用，但永不持久化。

| 层级 | 后端 | `BlobHandle.path` 前缀 | 选用时机 |
| --- | --- | --- | --- |
| 1 | OPFS（`FileSystemSyncAccessHandle`） | `opfs://` | `preferOpfs && isOpfsSupported()` |
| 2 | IndexedDB（原生 IDB，不依赖 Dexie） | `idb://` | `isIdbSupported()` |
| 3 | 内存（`Map<AssetId, Blob>`） | `memory://` | 始终可用，不持久化 |

`prepareImport(source)` 为三个后端共享：它提取 Blob、生成 `AssetId`、由 MIME 推断 `AssetType`，并异步拉取**丰富元数据**（图像 `dimensions` 通过 `createImageBitmap`，视频/音频 `duration` 通过 `HTMLMediaElement.loadedmetadata`，pdf `pages` 推迟到 Phase 2）。失败会被静默降级为 `undefined`，因此一段损坏的 EXIF 不会阻塞导入。

`wrapAssetStoreWithQuota(inner, quota)` 被无条件应用（即便对注入的存储也是如此）。它维护一个滚动 `usage` 计数器，并通过 promise 链（`runExclusive`）串行化 `import`/`create`/`remove`，使“检查并更新”窗口在并发下不会出现 TOCTOU。超大导入会抛出 `QuotaExceededError(usage, delta, quota)`。包装器还暴露 `_getQuotaUsage(): number`（在 `ensureInit` 完成前返回 `-1`），这样 `runtime.getStorageUsage()` 能以 O(1) 读取用量，而无需 O(n) 的 `listAssets()`。

### 2. CapabilityRegistry —— 解析流程

`CapabilityRegistry` 持有 `Map<CapabilityName, { capability, implementations[] }>`。两阶段注册与 Plugin 生命周期对齐：`registerCapability(capability)` 声明形状，随后 `registerImplementation(impl)` 挂载由引擎驱动的 `execute` 函数。

`resolve(name, preferredEngine?)` 是执行器对每个节点都会调用的热路径。它运行一个三阶段流水线：

<Mermaid source={`flowchart LR
  A["resolve(name, preferredEngine?)"] --> B{"implementations empty?"}
  B -- yes --> X["return undefined"]
  B -- no --> C["filter(i => i.status !== 'stub')"]
  C --> D{"available empty?"}
  D -- yes --> X
  D -- no --> E{"preferredEngine specified?"}
  E -- yes --> F["find(i => i.engine === preferredEngine)"]
  F -- found --> G["return impl"]
  F -- not found --> H["selectByStrategy(available)"]
  E -- no --> H
  H --> I{"defaultStrategy"}
  I -- first --> J["return available[0]"]
  I -- fastest --> K["rank by PERFORMANCE_RANK\nfast=0 medium=1 slow=2\nstable: ties keep registration order"]
  I -- balanced --> L["filter by capability.performance\nfallback to fastest if no match"]
  K --> G
  L --> G
`} />

`hasImplementation(name)` 和 `isStubOnly(name)` 让执行器能产出可操作的错误信息：仅含 stub 的能力会抛出 `"Install a real engine plugin to use this capability"`，而非笼统的 `"No implementation registered"`。

### 3. WorkflowExecutor —— 线性 DAG + node:finished → history

Year 1 仅支持线性工作流（无分支、循环、条件或并行）。执行器仍运行完整的 `topologicalSort(nodes, edges)`，因此未来支持 DAG 只是放松约束，而非重写。排序是防御性的：它拒绝重复节点 id、引用未知节点的边（包括 `__input__` 哨兵）、自环以及真实环，并给出精确错误信息。

单节点执行：

<Mermaid source={`sequenceDiagram
  participant R as Runtime.run()
  participant E as WorkflowExecutor
  participant CR as CapabilityRegistry
  participant EB as EventBus
  participant H as HistoryStack
  R->>E: execute(workflow, inputs)
  E->>EB: emit workflow:started
  loop transform nodes (topological order)
    E->>E: waitForResume() if paused
    E->>EB: emit node:started
    E->>CR: resolve(capability)
    CR-->>E: CapabilityImplementation
    E->>E: impl.execute(currentAssets, params, ctx)
    E->>EB: emit node:finished (outputs)
    EB-->>H: recordHistoryFromNodeEvent appends entry
  end
  E->>EB: emit workflow:completed
  E-->>R: WorkflowResult
`} />

`pause()` 通过一个 Promise resolver（`waitForResume`）挂起循环 —— 无轮询、无 CPU 开销。`cancel()` 翻转 `state.status = 'cancelled'`，调用 `abortController.abort()`（经由 `ExecutionContext.signal` 传播到每个引擎操作），并 resolve 被挂起的 resolver，使循环苏醒并中断。

`disposeWorkflow(workflowId)` 是 UI 在卸载时必须调用的清理入口：它取消任何运行中的执行、调用 `stack.reset()`（触发 `onEvict` 从 AssetStore 移除历史输出），并从 `historyStacks` / `initialInputsMap` / `currentOutputsMap` 中删除该工作流。不做这一步，长会话会同时泄漏 Map 条目和 OPFS blob。

### 4. HistoryStack —— 游标 + LRU 32 + IDB 持久化

每个工作流拥有自己的 `HistoryStack`。模型是一个数组上的游标：

- `cursor = -1` —— 初始状态，未应用任何条目
- `cursor = i` —— 条目 `i` 是当前已应用状态
- `append(entry)` —— 截断 redo 分支（`cursor + 1..end`），入栈，推进游标，若超过 `maxEntries`（默认 10）则驱逐 LRU
- `undo()` —— cursor--，返回新的当前条目（回到初始时为 `null`）
- `redo()` —— cursor++，返回新的当前条目
- `jumpTo(index)` —— 直接移动游标，供 HistoryPanel 点击跳转

`onEvict(entry)` 是资产回收钩子：Runtime 注册一个回调，为被驱逐条目的每个输出调用 `assetStore.remove(assetId)`，从而防止 OPFS 泄漏。`onChanged(workflowId, entries, cursor)` 会在 EventBus 上触发 `history:changed`，并触发 `persistHistory`（W7.2）。

**LRU 32。** Runtime 将 `historyStacks` 上限设为 `MAX_CONCURRENT_WORKFLOW_STACKS = 32`。超过上限时，最旧的栈（按 ES2015 规范，Map 的插入顺序）被 `reset()` 并删除。当前工作流绝不会成为受害者，因为 `enforceHistoryStacksLimit()` 在 `getOrCreateHistoryStack` 插入新条目之前运行。

**IDB 持久化。** 当 `enableIndexedDB` 为真时，`createHistoryStore()` 返回一个基于 IDB 的存储。`persistHistory(workflowId)` 快照 `{ entries, cursor, initialInputs, currentOutputs, updatedAt }`。`currentOutputs` 派生自快照（cursor 为 `-1` 时取 `initialInputs`，否则取 `entries[cursor].outputs`）—— 而非取自 `currentOutputsMap` —— 因为 `onChanged` 在 `append`/`undo`/`redo`/`jumpTo` 内同步触发，先于 Map 更新。

**`dirtyDuringLoad` 守卫。** 在 `loadPersistedHistory()` 期间，`restore()` 会再次触发 `onChanged` → `persistHistory`。一个在加载期间丢弃所有写入的朴素守卫会丢失来自并发 `run()`/`undo()` 调用的合法变更。修复办法：被跳过的工作流 id 被加入 `dirtyDuringLoad: Set<string>`，加载完成后每个都被重新持久化。

### 5. MemoryGuard + 降级阶梯

`MemoryGuard` 拒绝使用 `performance.memory`（仅 Chrome 可用、已废弃、MB 粒度），转而采用**显式追踪**：调用方在分配解码/Canvas 缓冲区时调用 `track(bytes)`，在丢弃时调用 `release()`。该句柄幂等 —— 重复 `release()` 是无操作。

| 压力等级 | 触发条件 | `shouldSpill()` | 典型阶梯级别 |
| --- | --- | --- | --- |
| `low` | ratio < 0.6 | false | L1-full |
| `elevated` | 0.6 ≤ ratio < 0.8 | false | L1-full |
| `high` | 0.8 ≤ ratio < 0.95 | true（若设置了 `assetStore`） | L2-tiled 或 L3-degraded |
| `critical` | 0.95 ≤ ratio | true | L3-degraded 或 L4-reject |

`estimateDecodedBytes(w, h)` 返回 `w * h * 4`（RGBA）—— 一张 4000×3000 的 JPEG 磁盘上约 2MB，但解码后约 46MB。改为追踪 `blob.size` 会严重低估压力。

`pickDegradation(ctx)` 是实现四级策略的**纯函数**：

| 级别 | 触发条件 | 策略 |
| --- | --- | --- |
| **L1-full** | `pressure ∈ {low, elevated}` | 全质量，正常处理 |
| **L2-tiled** | `pressure = high` + `canTile = true` | 基于分块的处理 + OPFS 溢出 |
| **L3-degraded** | `pressure = high` + 不可分块，或 `critical`（且缩放后估计 < 0.95×预算） | 输出上限设为 `DEGRADED_MAX_EDGE = 4096` + `DEGRADED_QUALITY = 70` |
| **L4-reject** | `critical` + 输入 > 预算 + 无溢出，或经 maxEdge 上限后解码估计仍 ≥ 0.95×预算 | 抛出 `DegradationRejectedError`，附带 `guide[]` |

`DegradationRejectedError.guide` 是一组用户可读的字符串数组（缩小源图像、关闭其他标签页、改用桌面应用）。UI 直接渲染它。`applyDegradationToResizeParams(params, decision)` 在 L3 激活时向 resize 参数注入 `maxEdge`。

## Worker 隔离协议

重计算（图像编解码、未来的 WASM 引擎）运行在专用 Web Worker 中，使主线程永远不会因 Canvas 工作而阻塞。跨源隔离（COOP/COEP）在 `apps/playground/public/_headers` 中配置，以为未来多线程 WASM 启用 `SharedArrayBuffer`。

`worker-protocol.ts` 是一个纯类型 + 守卫模块（与 `Worker` 无运行期耦合）：

- **Host → Worker：** `request`（按 id 索引的方法调用）、`ping`（心跳）、`cancel`（中止进行中的工作，W3.5）
- **Worker → Host：** `response`（成功/失败，按 id 关联）、`pong`、`event`（进度，无确认）、`ready`（携带 `protocolVersion` 握手）、`error`（致命，worker 存活但卡死）

`WorkerHost`（主线程）处理生命周期：带版本检查的 ready 握手、按请求超时（默认 60s）、周期性 ping（5s）及 pong 超时（15s）、崩溃检测（传输错误或心跳超时）、最多重启 `DEFAULT_MAX_RESTARTS = 3` 次后标记为 `dead`。`WorkerTransport` 接口抽象了浏览器 Worker / Node `worker_threads` / 测试 Fake，使协议与重启逻辑可在 Node 中单元测试。

`WorkerHost.request(method, params, signal?)` 接受 `AbortSignal`。中止时它发送 `WorkerCancel { type: 'cancel', id }` 并立即以 `WorkerRequestAbortedError` 拒绝 —— 它**不**等待 Worker 的响应。预检：已中止的信号在发送前即抛出。

## 四个扩展钩子

Runtime 为 SDK 和集成测试暴露了四个以下划线为前缀的钩子。它们不属于 `LokvisRuntime` 接口 —— 仅存在于 `LokvisRuntimeImpl` 上。

| 钩子 | 调用方 | 用途 |
| --- | --- | --- |
| `_getAssetStore()` | `@lokvis/sdk` `installPlugin` | 让插件共享 Runtime 的 AssetStore 进行 blob 读写 |
| `_getCapabilityRegistry()` | `@lokvis/sdk` `installPlugin` | 让插件调用 `registerCapability` / `registerImplementation` |
| `_getMemoryGuard()` | 集成测试 | 注入合成压力以验证 `BatchProcessor` 并发收缩 |
| `_registerMetadataReader(name, reader)` | `@lokvis/sdk`（从 `ctx.registerMetadataReader` 转发） | 注册只查询型 reader，如 `image.read-exif` |

MetadataReader 钩子是那些既不符合 Engine 的 Blob↔Blob 契约、也不符合 Capability 的 `Asset[]→Asset[]` 契约的只查询操作的长期归宿。`runtime.readAssetExif(id)` 在 readers 映射中查找 `'image.read-exif'`，若插件未安装则返回 `null` —— 不抛出，优雅降级。

## 有意未包含的内容

- **无 React / Redux 感知。** `eventBus.emit({ type: 'history:changed', ... })` 是唯一的旁路通道；UI 通过 `eventBus.on` 订阅。
- **无 Cloudflare / Cloud SDK 导入。** `lokvis-open` ↔ `lokvis-cloud` 的边界由包依赖强制约束，而非仅靠约定。
- **无 `performance.memory`。** 内存压力由显式 `track()` 调用驱动，使同样逻辑能在 Node 测试中运行。
- **无分支 / 循环 / 并行。** Year 1 执行器按设计为线性。DAG 形态的 `topologicalSort` 是向前兼容，而非过早设计。
