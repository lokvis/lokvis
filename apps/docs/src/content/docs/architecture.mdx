Lokvis follows a strict five-layer architecture with one-way dependencies. See `docs/whitepaper/04-技术架构设计.md` for the full spec.

## Layers

### 1. UI Layer

Astro 7 + React 19 + Tailwind v4. Renders the Workspace UI and tool pages.

### 2. Workflow Layer

Linear workflow executor (Year 1 only). Each workflow is a chain of `transform` nodes connected by edges. No branches, loops, conditions, or parallelism yet.

### 3. Runtime Layer

The "browser operating system". Single responsibility: `Input → Run → Output`. Manages assets, capabilities, history, and event bus. Never knows about React.

### 4. Capability Layer

`<domain>.<action>` naming convention (e.g. `image.resize`, `video.transcode`). Runtime never knows about FFmpeg — only about capabilities.

### 5. Engine Layer

Pluggable adapters wrap WASM libraries (Squoosh, ffmpeg.wasm, pdf-lib). The MVP image engine uses native browser Canvas + createImageBitmap for zero-dependency fastest first paint.

## Dependency Rules

- `lokvis-open` never imports from `lokvis-cloud`
- Runtime never knows about React / Redux
- Schema never knows about Runtime
- Plugin never knows about Cloud

## Storage

Metadata in IndexedDB (via Dexie in future), large files in OPFS (Origin Private File System). Runtime only manipulates AssetIds — never raw Blobs.

## Worker Isolation

All heavy computation (image encoding/decoding, future WASM engines) runs in a dedicated Web Worker, decoupled from the main-thread UI to prevent long tasks from blocking rendering (corresponding to whitepaper T1 "Browser memory/performance ★★★★★"). Cross-origin isolation (COOP/COEP) is configured in `apps/playground/public/_headers`, enabling `SharedArrayBuffer` for multi-threaded WASM.

### Communication Protocol (`@lokvis/runtime` worker-protocol)

Pure JSON messages, grouped by direction:

- **Host → Worker**: `request` (method call with id), `ping` (heartbeat)
- **Worker → Host**: `response` (correlated by id), `pong`, `event` (progress, etc.), `ready` (handshake), `error` (fatal error)

After startup, the Worker proactively sends `ready` (carrying the protocol version); the Host validates the version before sending any requests.

### Host Management (`WorkerHost`)

- **Request/Response**: Each request has a unique id; responses are correlated by id; each request has an independent timeout (default 60s).
- **Heartbeat and timeout**: The Host periodically sends `ping` (default 5s); the Worker must `pong` within the timeout (default 15s), otherwise it is treated as crashed.
- **Crash restart**: Transport-layer error / heartbeat timeout → terminate the current Worker, reject all pending requests, rebuild a new Worker (up to `maxRestarts` times, default 3). When the limit is exceeded, it enters `dead` and is handed to the upper layer for degradation.
- **Transport-layer abstraction**: The `WorkerTransport` interface abstracts over the differences between the browser Worker and the test Fake, allowing the protocol and restart logic to be verified in Node unit tests.

### Engine in Worker (`@lokvis/engine-image` worker-adapter)

## History Stack and undo/redo (`HistoryStack`)

Each workflow owns an independent `HistoryStack` that records a `HistoryEntry` for every transform step. undo/redo is implemented via a cursor: the cursor points to the last applied entry; appending a new operation truncates the redo branch after the cursor; when the limit (default 10 steps) is exceeded, the oldest entry is evicted via LRU and `onEvict` is called back to notify the caller to clean up the OPFS asset. Every change emits a `history:changed` event through the eventBus.

## Asset Storage and Three-tier Fallback (`AssetStore`)

The Runtime only manipulates `AssetId` and never holds Blobs directly. Asset storage is provided by the `createAssetStore()` factory, which auto-detects the best backend by priority: OPFS (best, supports `FileSystemSyncAccessHandle`) → IndexedDB (Dexie, persistent fallback) → in-memory (final fallback, non-persistent). Each backend is distinguished by the `BlobHandle.path` prefix (`opfs://` / `idb://` / `memory://`). The Runtime runs `checkStorageQuota()` before `run()` and throws `QuotaExceededError` when the quota is exceeded.

## Streaming and Memory Defense (W3: Streaming + Memory Defense)

A single browser tab has limited memory (typically 2-4GB on desktop, even less on mobile); batch processing of large images can easily trigger OOM crashes (the entire tab is killed, losing all intermediate results). W3 refines the all-or-nothing "either full or crash" decision into an observable, degradable memory-safety pipeline through four layers of mechanisms.

> Capabilities shipped in the Alpha stage (W12): 9 image-domain capabilities (resize / compress / convert / crop / rotate / flip / watermark / setBackground / filter) + 1 EXIF MetadataReader. The video/PDF/Audio engines are stubs and will be integrated in Phase 2. See `docs/capabilities.md`.

### Streaming Type Contracts (W3.1)

`engine-image/src/types.ts` defines streaming interfaces aimed at future WASM engines (line-by-line / chunked encoding and decoding):

- `ImageTile` / `ImageChunk`: tile geometry info and encoding results, consumed by the tiled pipeline on a per-tile basis.
- `StreamingImageOperation`: streaming operation signature that takes `ReadableStream<ImageTile>` as input and `WritableStream<ImageChunk>` as output.
- `StreamingImageEngineAdapter`: contract for the streaming engine adapter layer (`splitInput` / `processTile` / `mergeChunks`).

The Canvas engine cannot truly stream (`createImageBitmap` decodes in full once invoked), but the type contracts reserve integration points for the future Squoosh/WebCodecs WASM engine. The current Canvas engine approximates memory-peak control through the tiling infrastructure.

### Tile Processing Infrastructure (W3.2)

`engine-image/src/operations/tiles.ts` provides tiling primitives:

- `splitIntoTiles(width, height, tileSize=512)`: splits the image into a row-major grid; edge tiles align to the image boundary. A pure function, convenient for unit tests and deterministic regression.
- `mergeChunks(chunks, totalW, totalH, format, quality)`: merges the tile encoding results back into a single Blob (decode → drawImage onto an output canvas → encode).
- `isDownscale(srcW, srcH, targetW, targetH)`: determines whether the operation is a downscale, used to decide whether to take the `decodeResized` path.

`canvas-engine.ts` adds `decodeResized(blob, targetW, targetH)`: it uses the `resizeWidth`/`resizeHeight` options of `createImageBitmap` to scale during decoding, avoiding the cost of first decoding a full-resolution bitmap and then scaling — this is the Canvas engine's single biggest memory optimization. Browsers that do not support the resize option automatically fall back to a plain decode.

> **Design note**: resize takes the standard decode → computeTargetSize → drawImage path (single decode); `decodeResized` is exposed as a primitive reserved for future "explicit maxEdge"-style APIs or WASM engines. What W3.2 actually ships is the tiling infrastructure + streaming type contracts.

### Memory Guard (W3.3)

`runtime/src/memory-guard.ts` tracks the footprint of intermediate results and triggers OPFS spillover as it approaches the budget:

- **Explicit tracked accounting**: instead of relying on `performance.memory` (Chrome-only, deprecated, MB granularity), the caller explicitly registers `track(bytes)` at decode/canvas output and rolls back with `release()` (idempotent).
- **Four pressure levels**: `low` (&lt;60%) / `elevated` (60-80%) / `high` (80-95%) / `critical` (≥95%), based on `tracked / budget`.
- **OPFS spillover**: `shouldSpill()` returns true at `high`/`critical`; `spill(blob)` flushes the intermediate Blob to the AssetStore (OPFS-backed), `restore(asset)` reads it back on demand, and `evict(asset)` reclaims the space. This treats OPFS as virtual memory — keeping only the one or two currently active Blobs resident in memory.
- **Estimation helper**: `estimateDecodedBytes(w, h)` (w×h×4 RGBA) is used to track the real footprint of a decode result (a 4000×3000 JPEG blob may be only 2MB, but after decoding it occupies 46MB).

### Degradation Ladder (W3.4)

`runtime/src/degradation.ts` implements a four-tier degradation policy; the decision is the pure function `pickDegradation(ctx)`:

| Level | Trigger condition | Strategy |
|------|---------|------|
| **L1-full** | pressure = low / elevated | Full quality, normal processing |
| **L2-tiled** | pressure = high + operation is tileable | Tile processing + OPFS spillover of intermediate results |
| **L3-degraded** | pressure = high but not tileable, or critical | Degraded output: scale down to maxEdge (4096) + quality 70 |
| **L4-reject** | critical and unsalvageable even with degradation | Reject + throw `DegradationRejectedError` carrying user guidance |

L4 trigger condition: the input blob itself exceeds the budget and cannot be spilled, or the post-decode bitmap, even when scaled down by maxEdge, is still estimated at ≥ 0.95×budget. `DegradationRejectedError` carries a `guide` array (user-readable suggestions: use a smaller source image / close other tabs / use the desktop client), which the UI can render directly. `applyDegradationToResizeParams` applies the L3 decision to the resize params (injecting the `maxEdge` ceiling).

### Cancel Propagation (W3.5)

The `AbortSignal` is threaded all the way from the executor into engine operations, so `cancel()` actually aborts in-flight work instead of merely setting a flag:

1. **executor → plugin-image**: `execCtx.signal` is passed into `wrapAsImplementation.execute`.
2. **plugin-image → engine-image**: the `ImageOperation` type signature includes `signal?: AbortSignal`, and `wrapAsImplementation` forwards `execCtx.signal` to each operation.
3. **engine-image operations**: all operations (resize/crop/rotate/flip/compress/convert/watermark/setBackground/filter) call `throwIfAborted(signal)` at the decode / draw / encode boundaries. The binary-search loop of `compressToTargetSize` (6 rounds) checks before each round's encoding, avoiding expensive canvas encoding after cancellation. The `fetch(imageUrl)` in `watermark` also takes the signal to achieve network-layer cancellation.
4. **worker-host → worker-adapter**: `WorkerHost.request()` accepts `signal?: AbortSignal`; when abort is triggered, it sends a `WorkerCancel { type: 'cancel', id }` message and immediately rejects with `WorkerRequestAbortedError` (without waiting for the Worker to respond). An already-aborted signal throws before sending (pre-flight check).
5. **worker-adapter**: `startImageWorker` maintains an in-flight `Map<id, AbortController>` table; on receiving a `cancel` message it calls `controller.abort()` to abort the corresponding operation; `dispatchImageMethod` and `createImageWorkerHandler` pass the signal down to the operations.

`throwIfAborted(signal)` throws `DOMException('AbortError')`, consistent with Web platform conventions; the upper-layer executor already maps the cancelled state to `WorkflowResult.cancelled`.

## Workflow Orchestration (W10-W11)

Year 1 supports only linear workflows (up to 5 steps). `WorkflowBuilder` provides a chained API: `add(capability, params)` / `remove(nodeId)` / `move(from, to)` / `swap(a, b)` / `updateParams(nodeId, params)`, internally validating the 5-step limit (`MAX_WORKFLOW_STEPS = 5`). `build()` outputs a `Workflow` object, which is validated by `validateWorkflow()` for empty nodes / input-output connections / capability compatibility between adjacent nodes (three layers: the input node's inputTypes vs. workflow.inputs.type / adjacent nodes' outputTypes∩inputTypes / the output node's outputTypes).

The UI side, `@lokvis/ui-react`, provides:
- `WorkflowEditor.tsx`: HTML5 Drag and Drop API for drag-to-reorder + ← → keyboard movement + Delete to remove + InsertConnector hover-insert
- `useWorkflows.ts`: 5 free slots / unlimited on Pro + localStorage persistence + JSON import/export
- `useShareLink.ts`: `?workflow=<base64url>` share link (UTF-8 safe, handles Chinese watermarks)
- `data/workflow-templates.ts`: 5 built-in templates (web-optimize / social-batch / ecommerce-main / print-prep / screenshot-compress)

## Version and Compatibility (Alpha)

- **Runtime version**: `0.1.0` (`RUNTIME_VERSION` constant)
- **Workflow schema**: `v1` (within the share link `?workflow=<base64url>`: `{v:1, nodes:[...]}`)
- **MCP manifest version**: `2025-06-18` (MCP spec draft)
- **Worker protocol**: during the handshake the Worker sends `ready` carrying the protocol version; the Host validates it before communication begins
- **Engine version**: `canvasEngine.version = '0.1.0'`; stub engines have a `version` containing the `'stub'` marker; the Plugin layer's `wrapAsImplementation()` detects this and sets `CapabilityImplementation.status = 'stub'`, and `CapabilityRegistry.resolve()` automatically skips it

**Phase 1 Alpha known limitations** (not blocking Alpha; see `docs/reports/W12.1-alpha-acceptance.md` §5):
- L1: video/PDF/Audio engines are stubs (Phase 2 integrates ffmpeg.wasm / pdf-lib)
- L2: Plugin SDK is Alpha-only (ADR-O2; third-party plugins are not yet available; Phase 2 prioritizes the MCP server)
- L3: real-browser Lighthouse has not been run (a W16.5 task after the playground is deployed)
- L4: the internal Alpha test (5 people, 1 day) has not been conducted (W11.7 is a non-code task; execution is scheduled for the W12.7 buffer)
- L5: Sentry monitoring is integrated but no DSN is configured (landed in W12.3; `PUBLIC_SENTRY_DSN` is injected at deployment)
