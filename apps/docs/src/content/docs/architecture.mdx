Lokvis follows a strict five-layer architecture with one-way dependencies. See `docs/whitepaper/04-技术架构设计.md` for the full spec.

## Layers

### 1. UI Layer

Astro 7 + React 19 + Tailwind v4. Renders the Workspace UI and tool pages.

### 2. Workflow Layer

Linear workflow executor (Year 1 only). Each workflow is a chain of `transform` nodes connected by edges. No branches, loops, conditions, or parallelism yet.

### 3. Runtime Layer

The "browser operating system". Single responsibility: `Input → Run → Output`. Manages assets, capabilities, history, and event bus. Never knows about React.

### 4. Capability Layer

`<domain>.<action>` naming convention (e.g. `image.resize`, `video.transcode`). Runtime never knows about FFmpeg — only about capabilities.

### 5. Engine Layer

Pluggable adapters wrap WASM libraries (Squoosh, ffmpeg.wasm, pdf-lib). The MVP image engine uses native browser Canvas + createImageBitmap for zero-dependency fastest first paint.

## Dependency Rules

- `lokvis-open` never imports from `lokvis-cloud`
- Runtime never knows about React / Redux
- Schema never knows about Runtime
- Plugin never knows about Cloud

## Storage

Metadata in IndexedDB (via Dexie in future), large files in OPFS (Origin Private File System). Runtime only manipulates AssetIds — never raw Blobs.

## Worker 隔离(Worker Isolation)

所有重计算(图像编解码、未来 WASM 引擎)运行在独立 Web Worker 内,与主线程 UI 解耦,避免长任务阻塞渲染(对应白皮书 T1「浏览器内存/性能 ★★★★★」)。跨域隔离(COOP/COEP)在 `apps/playground/public/_headers` 配置,启用 `SharedArrayBuffer` 供多线程 WASM 使用。

### 通信协议(`@lokvis/runtime` worker-protocol)

纯 JSON 消息,按流向分两组:

- **Host → Worker**:`request`(带 id 的方法调用)、`ping`(心跳)
- **Worker → Host**:`response`(按 id 关联)、`pong`、`event`(进度等)、`ready`(握手)、`error`(致命错误)

Worker 启动后主动发 `ready`(携带协议版本),Host 校验版本后才开始发送请求。

### Host 管理(`WorkerHost`)

- **Request/Response**:每个请求唯一 id,响应按 id 关联;每请求独立超时(默认 60s)。
- **心跳与超时**:Host 周期性 `ping`(默认 5s),Worker 必须在超时(默认 15s)内 `pong`,否则视为崩溃。
- **崩溃重启**:传输层 error / 心跳超时 → 终止当前 Worker、拒绝所有 pending、重建新 Worker(最多 `maxRestarts` 次,默认 3)。超过上限进入 `dead`,交由上层降级。
- **传输层抽象**:`WorkerTransport` 接口屏蔽浏览器 Worker / 测试 Fake 差异,使协议与重启逻辑可在 Node 单测中验证。

## 历史栈与 undo/redo(`HistoryStack`)

每个工作流拥有独立的 `HistoryStack`,记录每一步 transform 的 `HistoryEntry`。undo/redo 通过 cursor(游标)实现:cursor 指向最后一条已应用的 entry;append 新操作时截断 cursor 之后的 redo 分支;超出上限(默认 10 步)时 LRU 淘汰最旧条目并回调 `onEvict` 通知调用方清理 OPFS 资产。每次变更通过 eventBus 发出 `history:changed` 事件。

## 资产存储与三级降级(`AssetStore`)

Runtime 只操作 `AssetId`,不直接持有 Blob。资产存储由 `createAssetStore()` 工厂按优先级自动探测最佳后端:OPFS(最优,支持 `FileSystemSyncAccessHandle`)→ IndexedDB(Dexie,持久化降级)→ 内存(最终降级,不持久化)。每个后端用 `BlobHandle.path` 前缀(`opfs://` / `idb://` / `memory://`)区分。Runtime 在 `run()` 前执行 `checkStorageQuota()`,超限抛 `QuotaExceededError`。

## 流式与内存防御(W3:Streaming + Memory Defense)

浏览器单 tab 内存有限(桌面典型 2-4GB,移动端更少),大图批量处理极易触发 OOM 崩溃(整个 tab 被杀,丢失所有中间结果)。W3 通过四层机制把"要么全量要么崩溃"的单点决策,细化为可观测、可降级的内存安全管线。

> Alpha 阶段(W12)已落地的能力目录:9 个 image 域能力(resize / compress / convert / crop / rotate / flip / watermark / setBackground / filter)+ 1 个 EXIF MetadataReader。视频/PDF/Audio 引擎为 stub,Phase 2 接入。详见 `docs/capabilities.md`。

### 流式类型契约(W3.1)

`engine-image/src/types.ts` 定义了面向未来 WASM 引擎(逐行/分块编解码)的流式接口:

- `ImageTile` / `ImageChunk`:分片几何信息与编码结果,供分片管线按 tile 处理。
- `StreamingImageOperation`:输入 `ReadableStream<ImageTile>`、输出 `WritableStream<ImageChunk>` 的流式操作签名。
- `StreamingImageEngineAdapter`:流式引擎适配层契约(`splitInput` / `processTile` / `mergeChunks`)。

Canvas 引擎无法真正流式(`createImageBitmap` 一旦调用就全量解码),但类型契约为后续接入 Squoosh/WebCodecs WASM 引擎预留了接入点。当前 Canvas 引擎通过分片基础设施近似实现内存峰值控制。

### 分片处理基础设施(W3.2)

`engine-image/src/operations/tiles.ts` 提供分片原语:

- `splitIntoTiles(width, height, tileSize=512)`:把图切成行优先网格,边缘 tile 对齐到图边界。纯函数,便于单测与确定性回归。
- `mergeChunks(chunks, totalW, totalH, format, quality)`:把分片编码结果合回单张 Blob(decode → drawImage 到输出 canvas → encode)。
- `isDownscale(srcW, srcH, targetW, targetH)`:判断是否为缩小,用于决定是否走 `decodeResized` 路径。

`canvas-engine.ts` 新增 `decodeResized(blob, targetW, targetH)`:使用 `createImageBitmap` 的 `resizeWidth/resizeHeight` 选项在解码阶段就缩放,避免先 decode 全分辨率位图再缩放——这是 Canvas 引擎最大的单点内存优化。不支持 resize 选项的浏览器自动回退到普通 decode。

> **设计备注**:resize 走标准的 decode → computeTargetSize → drawImage 路径(单次解码),`decodeResized` 作为导出原语留给未来"显式 maxEdge"型 API 或 WASM 引擎。W3.2 真正落地的是分片基础设施 + 流式类型契约。

### 内存守卫 MemoryGuard(W3.3)

`runtime/src/memory-guard.ts` 追踪中间结果占用,在逼近预算时触发 OPFS 溢出:

- **显式 tracked 计数**:不依赖 `performance.memory`(Chrome-only、deprecated、MB 粒度),而是由调用方在 decode/canvas 输出时显式 `track(bytes)` 登记,`release()` 回退(幂等)。
- **四级压力**:`low`(&lt;60%) / `elevated`(60-80%) / `high`(80-95%) / `critical`(≥95%),基于 `tracked / budget`。
- **OPFS 溢出**:`shouldSpill()` 在 `high`/`critical` 时为 true;`spill(blob)` 把中间 Blob 落到 AssetStore(OPFS-backed),`restore(asset)` 按需读回,`evict(asset)` 回收空间。把"OPFS 当虚拟内存用"——内存里只留当前活跃的一两个 Blob。
- **估算助手**:`estimateDecodedBytes(w, h)`(w×h×4 RGBA)用于追踪 decode 结果真实占用(一个 4000×3000 JPEG blob 可能只有 2MB,但 decode 后占 46MB)。

### 降级阶梯(W3.4)

`runtime/src/degradation.ts` 实现四级降级政策,决策是纯函数 `pickDegradation(ctx)`:

| 等级 | 触发条件 | 策略 |
|------|---------|------|
| **L1-full** | pressure = low / elevated | 完整质量,正常处理 |
| **L2-tiled** | pressure = high + 操作可 tile | 分片处理 + OPFS 溢出中间结果 |
| **L3-degraded** | pressure = high 但不可 tile,或 critical | 降级输出:缩到 maxEdge(4096)+ 质量 70 |
| **L4-reject** | critical 且即使降级也无救 | 拒绝 + 抛 `DegradationRejectedError` 携带用户引导 |

L4 触发条件:输入 blob 本身超预算且不可溢出,或解码后位图按 maxEdge 缩放估算仍 ≥ 0.95×budget。`DegradationRejectedError` 携带 `guide` 数组(用户可读建议:换更小源图 / 关闭其他 tab / 用桌面端),UI 可直接渲染。`applyDegradationToResizeParams` 把 L3 决策应用到 resize 参数(注入 `maxEdge` 上限)。

### Cancel 贯穿(W3.5)

`AbortSignal` 从 executor 一路贯穿到引擎操作,使 `cancel()` 真正中止在途工作而非仅置标志位:

1. **executor → plugin-image**:`execCtx.signal` 传入 `wrapAsImplementation.execute`。
2. **plugin-image → engine-image**:`ImageOperation` 类型签名纳入 `signal?: AbortSignal`,`wrapAsImplementation` 把 `execCtx.signal` 透传给每个操作。
3. **engine-image 操作**:所有操作(resize/crop/rotate/flip/compress/convert/watermark/setBackground/filter)在 decode / draw / encode 边界调用 `throwIfAborted(signal)`。`compressToTargetSize` 的二分循环(6 轮)每轮编码前检查,避免取消后继续做昂贵的 canvas 编码。`watermark` 的 `fetch(imageUrl)` 也传入 signal 实现网络层取消。
4. **worker-host → worker-adapter**:`WorkerHost.request()` 接受 `signal?: AbortSignal`;触发 abort 时发送 `WorkerCancel { type: 'cancel', id }` 消息并立即 reject `WorkerRequestAbortedError`(不等 Worker 回响应)。已 aborted 的 signal 在发送前直接抛错(pre-flight check)。
5. **worker-adapter**:`startImageWorker` 维护 `Map<id, AbortController>` 在途表;收到 `cancel` 消息时 `controller.abort()` 中止对应操作;`dispatchImageMethod` 与 `createImageWorkerHandler` 把 signal 下传给操作。

`throwIfAborted(signal)` 抛 `DOMException('AbortError')`,与 Web 平台约定一致,上层 executor 已将 cancelled 状态映射到 `WorkflowResult.cancelled`。

## Workflow 编排(W10-W11)

Year 1 仅支持线性工作流(最多 5 步)。`WorkflowBuilder` 提供链式 API:`add(capability, params)` / `remove(nodeId)` / `move(from, to)` / `swap(a, b)` / `updateParams(nodeId, params)`,内部校验 5 步上限(`MAX_WORKFLOW_STEPS = 5`)。`build()` 输出 `Workflow` 对象,经 `validateWorkflow()` 校验空节点 / 输入输出连接 / 相邻节点 capability 兼容性(三层:输入节点 inputTypes 与 workflow.inputs.type / 相邻节点 outputTypes∩inputTypes / 输出节点 outputTypes)。

UI 端 `@lokvis/ui-react` 提供:
- `WorkflowEditor.tsx`:HTML5 Drag and Drop API 拖拽重排 + 键盘 ← → 移动 + Delete 删除 + InsertConnector hover 插入
- `useWorkflows.ts`:5 槽位免费 / Pro 无限 + localStorage 持久化 + JSON 导入导出
- `useShareLink.ts`:`?workflow=<base64url>` 分享链接(UTF-8 安全,处理中文水印)
- `data/workflow-templates.ts`:5 个内置模板(web-optimize / social-batch / ecommerce-main / print-prep / screenshot-compress)
